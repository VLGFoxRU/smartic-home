# ТЕХНИЧЕСКОЕ ЗАДАНИЕ
## на разработку программного комплекса «SmarticHome — платформа управления умным домом»
### (SMARTICHOME/1.0)

---

## 1. Основание для разработки
Разработка программного комплекса SmarticHome обусловлена необходимостью создания централизованной системы мониторинга и управления устройствами умного дома с возможностью автоматизации и обнаружения аномалий для повышения комфорта, безопасности и энергоэффективности жилых помещений.

## 2. Назначение разработки
Создание веб-ориентированной платформы, обеспечивающей:
- сбор и визуализацию телеметрии с датчиков;
- управление исполнительными устройствами;
- настройку сценариев автоматизации;
- выявление аномальных событий;
- многопользовательский доступ с разграничением прав.

## 3. Цели разработки
- Реализация серверной части на Go (готовой к масштабированию).
- Создание современного веб-интерфейса на React.
- Обеспечение надёжного хранения временных рядов телеметрии в PostgreSQL.
- Внедрение механизмов автоматического обнаружения аномалий на основе статистических методов и пользовательских порогов.
- Предоставление инструментов для создания и выполнения сценариев автоматизации.
- Реализация подсистемы аудита действий пользователей и системных событий.

## 4. Требования к функциональным характеристикам
### 4.1. Управление пользователями и домами
- Регистрация и аутентификация пользователей с использованием JWT.
- Ролевая модель: владелец, администратор, контроллер, наблюдатель.
- Создание и управление домами, комнатами.
- Приглашение участников в дом с назначением ролей.

### 4.2. Управление устройствами
- CRUD-операции для устройств различных типов.
- Отправка управляющих команд с валидацией параметров.
- Отслеживание состояний устройств с кэшированием в Redis.

### 4.3. Сбор и визуализация телеметрии
- Приём показаний от датчиков.
- Хранение временных рядов в PostgreSQL (с возможностью подключения TimescaleDB).
- Получение истории показаний и последнего значения через API.
- Графическое отображение данных во фронтенде с выбором периода (24ч, 7д, 30д).

### 4.4. Сценарии автоматизации
- Создание, редактирование, активация/пауза, удаление сценариев.
- Условия: тип телеметрии, оператор сравнения, пороговое значение.
- Действия: отправка команды на целевое устройство.
- Автоматическое выполнение сценариев при поступлении новых показаний.
- Защита от повторных срабатываний.

### 4.5. Обнаружение аномалий
- Статистический детектор: расчёт среднего и стандартного отклонения за 7 дней, выявление выбросов.
- Пороговый детектор: создание пользовательских порогов (мин/макс) с указанием уровня критичности.
- Автоматическая запись аномалий и уведомление через WebSocket.

### 4.6. Уведомления в реальном времени
- WebSocket-сервер для рассылки событий.
- Отображение всплывающих уведомлений в веб-интерфейсе (Toast).

### 4.7. Аудит
- Логирование всех управляющих действий пользователей и системных событий в таблицу `audit_log`.
- Хранение идентификатора пользователя, типа действия, временной метки, корреляционного идентификатора.

### 4.8. Пользовательский интерфейс
- Дашборд с карточками домов и комнат, отображением последних показаний датчиков.
- Страница дома со списком устройств, кнопками управления, модальными окнами для добавления комнат и устройств.
- Страница устройства с графиком телеметрии, текущим значением и списком аномалий.
- Управление сценариями и аномалиями с возможностью изменения статусов.
- Тёмная/светлая тема, кнопка копирования ID, подтверждение удаления.

## 5. Требования к надёжности
- Гарантированное сохранение телеметрии и аудита при штатной работе.
- Кэширование состояний устройств в Redis для снижения нагрузки на БД.
- Оптимистическая блокировка для предотвращения конфликтов параллельных изменений.

## 6. Условия эксплуатации
- Веб-доступ через современные браузеры (Chrome, Firefox, Edge).
- Развёртывание с использованием Docker Compose.

## 7. Требования к составу и параметрам технических средств
- **Серверная часть:** Go 1.24+, PostgreSQL 15+, Redis 7.
- **Клиентская часть:** Node.js 20+, React 19.
- **Контейнеризация:** Docker, Docker Compose.
- **Минимальные аппаратные требования:**
  - Процессор: 2 ядра, 2 ГГц
  - ОЗУ: 4 ГБ
  - Дисковое пространство: 20 ГБ
- **Рекомендуемые:**
  - Процессор: 4 ядра, 3 ГГц
  - ОЗУ: 8 ГБ
  - Дисковое пространство: 50 ГБ (SSD)

## 8. Требования к информационной и программной совместимости
- Соответствие стандартам HTML5, CSS3.
- API соответствует принципам REST, обмен данными в формате JSON.
- Поддержка аутентификации через JWT.

## 9. Стадии и этапы разработки
1. **Проектирование архитектуры** – определение компонентов, схемы БД, API.
2. **Разработка ядра системы** – реализация доменной модели, сервисов управления устройствами, телеметрии, сценариев, аномалий.
3. **Создание веб-интерфейса** – дашборд, страницы дома и устройства, управление сценариями и аномалиями.
4. **Реализация системы уведомлений** – WebSocket, Toast.
5. **Тестирование и отладка** – функциональное тестирование, проверка безопасности, нагрузочное тестирование.
6. **Документирование** – подготовка README, технического задания, коллекции Postman.

## 10. Порядок контроля и приёмки
- Функциональное тестирование всех модулей по сценариям использования.
- Проверка безопасности (JWT, ролевая модель, защита от инъекций).
- Приёмочные испытания с участием конечных пользователей.
- Анализ соответствия требованиям ТЗ.

# ОПИСАНИЕ ПРОГРАММЫ
## «SmarticHome — платформа управления умным домом»

### 1. Общие сведения
**1.1. Обозначение и наименование программы**
- Обозначение: `SMARTICHOME/1.0`
- Наименование: «SmarticHome — платформа управления умным домом»
- Краткое наименование: SmarticHome

**1.2. Программное обеспечение, необходимое для функционирования**
- Серверная часть:
  - Go 1.24+ (сборка и запуск)
  - PostgreSQL 15+
  - Redis 7
  - Docker, Docker Compose (для контейнеризации)
- Клиентская часть:
  - Веб-браузер с поддержкой HTML5, CSS3, JavaScript ES6+
  - Node.js 20+ (для сборки)

**1.3. Языки программирования**
- Go (серверная бизнес-логика)
- JavaScript/React (клиентский интерфейс)
- SQL (работа с базой данных)

### 2. Функциональное назначение
**2.1. Класс решаемых задач**
Программа предназначена для:
- мониторинга параметров окружающей среды и потребления ресурсов;
- дистанционного управления бытовыми устройствами;
- автоматизации рутинных операций по заданным правилам;
- раннего обнаружения нештатных ситуаций (аномалий);
- предоставления аналитики и истории для принятия решений.

**2.2. Назначение программы**
SmarticHome обеспечивает централизованное управление устройствами умного дома через веб-интерфейс с возможностью настройки автоматических сценариев, отслеживания аномалий и анализа накопленных данных.

**2.3. Функциональные ограничения**
- Не является системой реального времени для критически важных процессов.
- Для полноценной работы требует развёртывания всех компонентов (БД, Redis, API).
- Детектор аномалий на основе статистики требует накопления не менее 10 записей для каждого показателя.

### 3. Описание логической структуры
**3.1. Алгоритм работы программы**
1. Пользователь регистрируется/входит в систему.
2. Создаёт дом, комнаты, добавляет устройства.
3. Устройства отправляют телеметрию (или она эмулируется вручную).
4. При поступлении нового показания:
   - данные сохраняются в БД;
   - проверяются условия сценариев (SceneEngine) и пороги/статистика (AnomalyDetector);
   - при срабатывании создаются аномалии или выполняются команды;
   - через WebSocket рассылаются уведомления.
5. Пользователь может просматривать историю, управлять устройствами вручную, менять статусы аномалий.

**3.2. Используемые методы**
- Чистая архитектура (разделение на domain, service, handler, infrastructure).
- JWT-аутентификация.
- REST API.
- WebSocket для двусторонней связи.
- Кэширование (Redis) для состояний устройств.

**3.3. Структура программы**
**3.3.1. Основные модули (серверная часть)**
- `cmd/api` – точка входа.
- `internal/domain` – сущности и бизнес-правила.
- `internal/repository` – интерфейсы для работы с данными.
- `internal/infrastructure` – реализации (PostgreSQL, Redis, WebSocket).
- `internal/service` – слой бизнес-логики.
- `internal/handler` – HTTP-обработчики и DTO.
- `internal/middleware` – аутентификация, CORS, логирование.
- `internal/engine` – движок выполнения сценариев.
- `internal/detector` – детектор аномалий.

**3.3.2. База данных**
Основные таблицы: `users`, `homes`, `rooms`, `devices`, `device_states`, `telemetry`, `anomalies`, `scenes`, `alert_thresholds`, `audit_log`, `home_members`.

**3.4. Связи с другими программами**
- Веб-браузер (клиент).
- Docker-контейнеры (PostgreSQL, Redis).
- Внешние IoT-шлюзы (через брокер сообщений, *в перспективе*).

### 4. Используемые технические средства
**4.1. Аппаратные требования** (см. п. 7).

**4.2. Программные платформы**
- ОС: Linux, Windows, macOS.
- Веб-сервер: встроенный в Go (net/http).
- СУБД: PostgreSQL 15+.
- Кэш: Redis 7.

### 5. Вызов и загрузка
**5.1. Способ вызова программы**
- Бэкенд: через `docker compose up` в папке `backend`.
- Фронтенд: через `npm run dev` в папке `frontend`, затем открыть `http://localhost:5173`.

**5.2. Входные точки API** (основные)
- `/api/v1/auth/register`, `/login`, `/me`, `/change-password`
- `/api/v1/homes`, `/homes/{id}/rooms`, `/devices`, `/devices/{id}/command`
- `/api/v1/telemetry/{id}`, `/telemetry/{id}/latest`
- `/api/v1/scenes`, `/scenes/{id}/activate`, `/pause`
- `/api/v1/anomalies`, `/anomalies/{id}`
- `/api/v1/thresholds`
- WebSocket: `ws://localhost:8080/ws?token=...`

**5.3. Требования к памяти**
- Один экземпляр API Gateway: ~50 МБ ОЗУ.
- Redis: до 64 МБ.
- PostgreSQL: зависит от объёма данных, минимально 64 МБ.

### 6. Входные данные
**6.1. Характер и организация входных данных**
- Данные пользователей: логин, пароль, email.
- Данные телеметрии: тип, значение, временная метка.
- Команды управления: тип команды, параметры (JSON).
- Конфигурация сценариев и порогов: условия и действия.

**6.2. Формат и способ кодирования**
- Все HTTP-запросы/ответы: JSON, кодировка UTF-8.
- Токены аутентификации: JWT (HS256).

### 7. Выходные данные
**7.1. Характер и организация выходных данных**
- Списки сущностей (дома, устройства, аномалии) в формате JSON.
- Временные ряды телеметрии для построения графиков.
- WebSocket-сообщения о событиях.

**7.2. Формат и способ представления**
- Веб-интерфейс: графики (Chart.js), списки, карточки.
